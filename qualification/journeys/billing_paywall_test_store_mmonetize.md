# Billing Paywall Test Store journey (CHE-9833)

This is a provisional, text-only testcase candidate. It does not run Artemis, build or install an APK, or use a device or ADB. Execution is NOT-RUN and requires approval of this exact journey and manifest revision by two independent non-author reviewers, followed by a separate Android device admission.

Case E uses a separately built `adsTestDebug` APK with that key absent. `adsReal` is out of scope. ## Admission and fixture

Before any device command, the Android device leader must grant the exact target, serial, permitted actions, evidence destination, executor and cleanup owner. The leader selects the device class; this candidate does not claim a device or qualify a runner.

For each case, start from clean app data using `adb -s <device_serial> shell pm clear io.mmonetize.sample`, then open the sample and select **Paywall — Real offering**. `pm clear` clears app data; it is not an APK install. If the package is absent, install only the APK admitted for the execution issue, then establish the clean state before continuing. Do not clear another package or shared device state.

Cases A–D need the configured RevenueCat Test Store build and the existing `che801_test` offering. Before A, the execution operator records every package identifier and product identifier in `che801_test` from the RevenueCat dashboard, then compares the complete list with the visible plan list. The monthly package must map to product `che801_premium_monthly_test`; record its RevenueCat package identifier from the dashboard rather than assuming a package identifier. Never record or expose a key in testcase evidence.

The execution operator reads the RevenueCat customer state in the RevenueCat dashboard, opening the customer identified by the exact App User ID for that case and recording whether `premium` is active. Record the App User ID only in access-controlled execution evidence; redact it in shared screenshots. If the dashboard cannot identify one customer unambiguously, the customer-state assertion is `NOT-RUN` and the case is BLOCKED. Do not use an API key or another case's customer state.

For configured cases, retain the app log line whose message exactly matches `initBilling: billing/core initialized`; match the message text regardless of Android log tag. This line confirms billing initialization only and is not an action oracle. Use the case-specific UI and RevenueCat evidence below for behavior. Case E has no logcat success oracle; capture the complete startup log window and verify that the initialization message is absent.

Timing limits: allow 60 seconds after opening the entry for the paywall or not-configured screen to appear; allow 120 seconds after starting purchase or restore for the Test Store flow and resulting UI to complete; after a cancellation dialog closes, observe the paywall and error state for 30 seconds. A missing completion anchor at the deadline is BLOCKED (timeout), not a pass. Capture screen recording continuously from before the purchase or restore action through its completion so a short toast cannot be missed.

## Cases

For each case, retain privacy-safe screenshots or screen recording, the specified log evidence, the RevenueCat customer evidence or explicit `NOT-APPLICABLE`, this testcase revision, the selected build's source SHA and APK SHA-256, the exact device serial and command exit status. Record missing or contradictory evidence as BLOCKED or FAIL; do not infer a pass from a model summary or a screenshot alone.

1. **A — Offering and prices.** With clean app data, open **Paywall — Real offering** within 60 seconds. Assertion: `The plan list shows every recorded che801_test package and its localized Test Store price.` Compare each visible plan with the dashboard package/product list recorded before the run; record visible names and prices without hard-coding locale-specific prices. Require the exact log message `initBilling: billing/core initialized`. A missing screen or incomplete package list is FAIL; a 60-second timeout is BLOCKED.
2. **B — Purchase.** Select the recorded monthly package mapped to product `che801_premium_monthly_test` and start the Test Store purchase. Assertion: `The Premium active toast appears in the continuous screen recording, BillingPaywallDemoActivity closes, and premium is active for the identified RevenueCat customer.` Require the exact log message `initBilling: billing/core initialized`. The completion anchor is the toast in the recording plus the activity leaving the foreground, checked in the same recording and by a UI hierarchy capture showing the prior screen within 120 seconds. Read `premium` in the dashboard for the App User ID associated with this purchase. Missing toast, closure, or active entitlement is FAIL; timeout or ambiguous customer identity is BLOCKED.
3. **C — Restore.** After B, record B's exact RevenueCat App User ID from the dashboard. Clear only `io.mmonetize.sample` app data with `pm clear`, reopen the sample and enter **Paywall — Real offering** within 60 seconds. Before tapping **Restore**, identify the current App User ID from the RevenueCat dashboard and compare it exactly with B. If it differs or cannot be identified unambiguously, mark C `NOT-RUN` and BLOCKED; do not claim restore success. If it matches, tap **Restore**. Assertion: `Restore displays Active, the Premium active toast is captured in the continuous screen recording, BillingPaywallDemoActivity closes, and premium is active for the same App User ID as B.` The completion anchor is the visible Active result/toast and activity closure within 120 seconds; capture the UI hierarchy after closure and read entitlement in the dashboard. Require the exact log message `initBilling: billing/core initialized`. Timeout is BLOCKED; a completed flow with a missing expected result is FAIL.
4. **D — Cancel.** With clean app data, open the real offering within 60 seconds, identify the current App User ID in the RevenueCat dashboard, select the recorded monthly package and cancel in the Test Store dialog. Assertion: `The dialog dismisses, no purchase error appears during the following 30 seconds, the paywall remains open, and premium is inactive for this case's identified customer.` The completion anchor is dialog dismissal; capture the screen and observe the full 30-second window, then read that customer's entitlement in the dashboard. Require the exact log message `initBilling: billing/core initialized`. If the customer cannot be identified, entitlement is `NOT-RUN` and the case is BLOCKED. Timeout is BLOCKED; an error, closed paywall, or active entitlement is FAIL.
5. **E — Billing not configured.** Use the separate `adsTestDebug` build with no RevenueCat key. Open **Paywall — Real offering** within 60 seconds. Assertion: `The Billing is not configured message appears and billing initialization is skipped.` Capture the screen and full startup log window; verify `initBilling: billing/core initialized` is absent. Entitlement evidence is `NOT_APPLICABLE: billing not initialized`, supported by the screen and absence of the initialization log; do not query or reuse another customer. Do not enter a Test Store purchase flow. Timeout is BLOCKED; an initialized billing message or missing configuration message is FAIL.
